# 11 容量复验、灰度发布与回滚

Type: task
Status: claimed
Stage: 收费发布
Blocked by: 10

## 目标

用生产规格建立容量基线，通过小流量灰度发布，并证明可以在规定时间内回滚应用且不破坏数据库事实。

## 问题分析

- 既有 100 并发 `/readyz` 数据来自本机 Docker，只能作为起点。
- HTTP RPS 不能代表 Provider 每分钟完成任务数、数据库连接峰值或媒体 I/O。
- Alembic 自动升级后，简单切换旧镜像可能因数据库 schema 不兼容而失败。
- 图片请求已经发送后不能保证物理取消，回滚不得导致重复提交或重复计费。

## 设计方案

- 分层压测：就绪探针、登录、画布保存、任务提交/SSE、媒体读取、Provider 完成吞吐分别测量。
- 监控 60 条应用连接预算、数据库预留、队列最老年龄、Worker 利用率和 Provider 配额。
- 使用不可变摘要部署，灰度按内部账号 → 小比例用户 → 全量推进，每阶段有自动停止阈值。
- 数据库变更遵循 expand/contract；发布前验证旧镜像与新 schema 的兼容窗口。
- 回滚只切换镜像/流量，不回退账务与任务事实；数据库 downgrade 需要独立审批。

## 实施步骤

### 1. 分析问题

- 建立生产规格容量模型和 Provider 配额表，确认测试不会产生不可控费用。
- 对最新迁移做向前/向后兼容分析，列出不能快速回滚的变更。

### 2. 设计确认

- 评审压测场景、数据清理、成本上限、灰度阶段、停止阈值和回滚责任人。
- 定义发布成功观察窗口和业务 SLO。

### 3. 修改代码

- 扩展容量脚本或引入 k6/Locust，覆盖认证会话、SSE 和代表性业务路径。
- 新增发布、灰度、状态快照和回滚脚本；记录前后镜像 digest 与迁移 head。
- 编写数据库兼容与 Worker 优雅停止检查。

### 4. 质量检测

- 在生产同规格预发布环境执行 100 并发及持续稳定性测试，记录 p95/p99/RPS/错误率/连接数。
- 验证 Provider 完成吞吐、队列恢复速度和成本上限。
- 实际演练新版本 → 触发停止阈值 → 回滚旧镜像，确认 queued/running/unknown 任务不重复提交。

## 完成标准

- 容量指标达到批准基线且 PostgreSQL 保留足够连接余量。
- 灰度阈值、观察窗口和负责人明确。
- 最近一次回滚演练在目标时间内完成，账务、任务和媒体一致。
- 发布后完成检查表并记录最终生产镜像 digest。

- 新增非敏感发布状态快照，记录镜像 digest、迁移 head 和时间；脚本不会执行流量切换或数据库 downgrade。
