# 严格用户顺序与绝对生图截止

Type: task
Status: resolved

## Problem

- 同一用户允许多个批次同时进入上游，后提交任务可能先完成。
- 批量任务虽然逐张请求，但用户端把所有未完成位置都显示为“正在生图”。
- HTTP/SSE 读取超时会被心跳刷新，导致上游请求越过任务绝对截止时间后仍继续运行。
- 多参考图近期集中出现超时或 SSE 没有最终图片；生产路由存在高于已验证协议上限的配置。

## Decision

- 当账户执行并发为 1 时，Worker 只允许最早的 queued 任务进入执行，并在锁内再次校验 FIFO。
- Provider 请求携带任务活动回调；任务超时、失败或取消后终止当前读取，并不再发送批量中的后续图片请求。
- Provider 的 `request_timeout_seconds` 同时作为绝对时限，SSE 心跳不能刷新该时限。
- 用户端对运行中批量任务只把当前一张显示为“正在生图”，后续显示“等待前一张完成”。
- 管理员生成容量页明确展示从何时计时、多少分钟/秒算超时、超时后的退款和迟到结果规则。
- 生产 `gpt-image-2` 参考图上限恢复为 3，并在路由编辑页提示上游兼容性风险。

## Answer

- 问题账户执行并发已从 3 调整为 1；Worker 在候选查询和账户锁内都校验最早 queued 任务，单槽账户不会被后任务抢跑。
- 批量任务仍逐张 `n=1` 请求；运行中只有当前图片显示“正在生图”，其余显示“等待前一张完成”。
- Provider 请求增加任务活动回调，超时、失败或取消后终止读取且不发送剩余图片请求。
- `request_timeout_seconds` 现为绝对时限，SSE 心跳不能刷新；异步轮询也共用同一绝对截止点。
- 管理员生成容量页显示当前分钟数和秒数、计时起点、超时中止、退款及迟到结果作废规则；模型路由页同步解释 Provider 绝对超时。
- `gpt-image-2/满血4k` 生产参考图上限已从 16 恢复为 3；1K 与满血4k 当前均为 3。
